# Windows Packaging

The release build uses `jpackage` with a JRE generated from Java 21 `jlink` output. The packaged application contains application classes and resources only. yt-dlp and FFmpeg must be obtained from official releases, with their exact versions and licenses recorded in `tools/README.md` before packaging.

Expected runtime layout:

```text
VideoDownloader/
├── app/
├── runtime/
└── tools/
    ├── yt-dlp.exe
    └── ffmpeg.exe
```

Configuration is stored below `%APPDATA%/NZSK/VideoDownloader/`; logs are stored below `%LOCALAPPDATA%/NZSK/VideoDownloader/logs/`. Upgrades replace the application installation while preserving user configuration and downloads.

Inside the application image, `app/` contains the two module jars and their dependencies, `runtime/` contains
the reduced Java 21 runtime, and `tools/` receives `yt-dlp.exe` and `ffmpeg.exe` when those files exist in the
repository `tools/` directory. Tool paths can also be configured in the settings page and are stored in
`config.json`.

The executable icon comes from `packaging/windows/icon.ico`, generated by `utils/make-icon.ps1`. The optional
design master is `tubiao.png` in the project root; when it is absent the script falls back to the existing
`project/frontend/src/main/resources/icon.png`, so a build never depends on an untracked master file. The
script writes a multi-size ICO (16 to 256 pixels) plus the 256x256 PNG that the JavaFX window uses as its icon
resource. `build-windows.ps1` passes the ICO to `jpackage --icon` and warns without failing when the file is
absent.

The build also copies `LICENSE` and `THIRD-PARTY-NOTICES.md` into the application image root, so any
redistributed copy carries the license and third-party notices. Keep them in place and keep
`runtime/legal/` intact; together they satisfy the licensing obligations recorded in
`THIRD-PARTY-NOTICES.md`.

## Build procedure

Run `utils/build-windows.ps1` from PowerShell with Java 21 in `JAVA_HOME`. The script runs `:project:frontend:installDist`, creates a reduced Java 21 runtime with `jlink`, and produces a Windows application image with `jpackage` under `packaging/windows/output/VideoDownloader`.

The script does not download yt-dlp or FFmpeg. Place binaries obtained from their official releases in `tools/` only after recording their exact versions, checksums, and licenses in `tools/README.md`.

The current build is an application image. A future release can replace `--type app-image` with `--type exe` after the Windows packaging toolchain and vendor installer policy are finalized. Upgrades should install the new application image over the existing installation while retaining `%APPDATA%/NZSK/VideoDownloader/` and `%USERPROFILE%/Downloads/VideoDownloader/`.

The packaged entry point is `com.nzsk.videodownloader.ui.VideoDownloaderLauncher`, a plain class that calls the
JavaFX application. The JVM rejects a main class that extends `javafx.application.Application` when JavaFX is
placed on the classpath (as `jpackage` does for a non-modular image), so the launcher class is required.
